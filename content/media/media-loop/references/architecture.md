# 媒体运营技能架构

## 1. 体系目标

这套技能把媒体运营拆成四个相互协作、职责独立的层次：

```text
外部定时器/用户请求
        ↓
     media-ops  ←→  media-loop
        ↓              ↓
   平台子技能       media-core
        ↓              ↓
   平台发布结果   内容资产与资源
```

目标不是“每次触发都发布”，而是让每一次运营运行都能回答：

- 当前账号和平台是否健康；
- 是否有合格的内容和媒体资产；
- 当前目标应该发布、补货、适配、暂停还是等待；
- 失败后能否从原阶段恢复而不重复产生副作用；
- 平台数据是否足以支持下一轮策略改进。

## 2. 四层职责

### `media-loop`：运营反馈与策略闭环

负责回答“下一步运营需要什么”：

- 读取发布结果、平台指标、账号健康状态和内容库存；
- 区分账号分发、内容供给、平台适配和内容表现问题；
- 诊断空队列、适配积压、连续失败和效果下降；
- 生成有证据的 `adaptationRequest`、`productionRequest` 和 `strategyOverride`；
- 管理基线、实验、健康状态、暂停条件和复盘时间；
- 发现执行异常时协调恢复，但不直接发布、不下载素材、不管理凭证。

### `media-core`：内容资产与资源生产层

负责回答“内容是否真实、完整、可复用”：

- 管理来源、来源协议、候选、证据卡、事实边界和版权状态；
- 发现、核验和按授权规则采集媒体资源；
- 维护内容资产、媒体指纹、顺序游标和生命周期；
- 把已核验内容分别适配为各平台分发目标；
- 处理 `media-loop` 的适配和生产请求；
- 不登录平台、不发布、不决定账号推荐策略。

### `media-ops`：执行编排与发布总控层

负责回答“本轮是否可以安全执行”：

- 解析账号、平台、来源、策略、Profile 和传输通道；
- 统一执行 preflight、目标选择、运行锁、幂等和发布门禁；
- 调用 `media-loop` 处理运营反馈和供给缺口；
- 调用 `media-core` 准备内容，再调用平台子技能适配和发布；
- 核对账号身份、版权、事实、重复、限流、成功信号和写回；
- 处理浏览器临时页面清理；
- 不自行发现候选、不绕过内容层、不自行猜测平台算法原因。

### 平台子技能：平台适配与平台交互层

包括 `x`、`x-api`、`xiaohongshu` 和 `douyin`：

- 根据平台机制筛选和改编内容；
- 生成平台独立的标题、正文、脚本、媒体和互动入口；
- 执行平台特有的账号核验、页面/API 交互和发布结果核验；
- 解释平台专属指标和限制；
- 不负责跨平台调度、来源游标、账号长期策略或凭证管理。

## 3. 数据所有权

| 数据 | 唯一责任方 |
|---|---|
| 账号定位、平台身份、执行策略 | `media-ops` 配置 |
| 运营健康、基线、实验、策略反馈 | `media-loop` |
| 来源、候选、事实、版权、媒体、游标 | `media-core` |
| 内容资产与分发目标 | `media-core` |
| 发布状态、运行锁、传输状态 | `media-ops` |
| 平台文案、平台媒体和平台结果 | 对应平台子技能 + `media-ops` 回写 |
| 密码、Cookie、Token、验证码 | 外部运行环境，技能不得读取或保存 |

平台目录中的发布记录可以作为审计和指标历史，但不能覆盖内容层的事实、版权和资产状态。

## 4. 一次运营运行的生命周期

```text
触发
 → preflight
 → 读取检查点/运行锁
 → 选择内容目标
 → 检查账号健康与库存
 → 恢复适配积压或请求生产
 → 内容核验与平台适配
 → ready admission
 → 平台发布门禁
 → 创建草稿/上传/提交
 → 成功、审核中、失败或待确认
 → 写回内容、平台和 loop 记录
 → 清理本轮临时页面
 → 进入下一次复盘
```

外部定时器控制运行触发次数；一次运行默认最多发布一个目标。定时器触发不代表必须发布，任何硬门禁失败都应安全跳过或暂停。

## 5. 关键边界

- `verified` 不等于 `ready`；事实核验完成后仍需完成目标级平台适配。
- `productionRequest` 不是发布授权；`asset_ready` 也不等于发布成功。
- `published_pending_review` 和 `unknown` 不能通过重新发布解决。
- 一个账号的健康状态不能与另一个逻辑账号合并；跨平台指标不能直接横向排名。
- 一个来源 pipeline 只能有一个事实写入者；所有触发器必须进入同一决策入口并使用运行锁。
- 平台失败不能扩散为同一内容其他平台目标失败。
- 策略优化不能关闭事实、版权、安全、去重、账号身份、限流和成功核验门禁。
- 永久配置修改必须有用户明确授权；普通反馈只产生临时覆盖或实验建议。

## 6. 自我完善机制

闭环分为两条链：

### 运营技术链

```text
执行异常
 → 检查点定位
 → 最小范围恢复
 → 重新执行受影响门禁
 → 写入原因和恢复条件
```

关注成功率、恢复率、重复动作、空转率、平均运行时长、待确认比例和各阶段阻塞原因。

### 运营质量链

```text
平台数据
 → 数据质量检查
 → 同账号同平台基线
 → 归因诊断
 → 单变量实验
 → 策略覆盖
 → 下一轮验证
```

关注曝光、点击、停留、完播、互动、收藏、分享、主页访问、关注转化和负向反馈。样本不足时只能保留假设，不能把单条爆款或单次失败写成长期规律。

## 7. 失败处理原则

所有失败必须归类并保留下一步：

- **可恢复技术失败**：恢复当前阶段，不能重跑整条链路；
- **硬门禁失败**：保留资产，等待条件满足；
- **结果不明确**：只读核验，禁止重复写操作；
- **供给不足**：由 `media-loop` 判断是否适配积压或有界补货；
- **数据不足**：补采数据，不进行强结论归因；
- **账号健康风险**：暂停账号队列，不能用新内容覆盖风险。

每次运行都应留下可恢复的记录：做到了哪一步、产生了哪些副作用、为什么停止、下次从哪里继续。
