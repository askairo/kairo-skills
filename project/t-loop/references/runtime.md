# 临时子 Agent 运行方式

## 能力发现

先按 `SKILL.md` 判断宿主：Grok Bot、Hermes 等 Bot 体系默认使用自身编排，不自动调用本技能，不为此安装子 Agent 扩展或联系现有 Bot；用户明确选择本次使用 t-loop 时才继续。

本技能需要主会话真正创建独立子 Agent、派发任务并接收结果。检查宿主实际暴露的工具及说明，而非仅凭产品名、已安装 skill 或多个角色名称判断能力存在。

当前宿主若提供原生 collaboration，可用创建、消息、结果通知、续派和中断工具；工具名称依实际环境确认。不要调用不存在的“销毁”方法。跨 provider/机器协作只有在用户要求且相关能力实际可用时使用，继续遵守原授权范围。

### 缺少子 Agent 能力

1. 先核对宿主版本、配置与官方文档，区分能力未启用和需要额外扩展；有原生能力就启用，不重复安装。
2. 需要扩展时，先安装官方提供或官方文档明确给出的子 Agent 扩展，再执行 t-loop。以 [Pi 官方子 Agent 扩展示例](https://github.com/badlogic/pi-mono/tree/main/packages/coding-agent/examples/extensions/subagent) 为例，按当前官方安装说明操作，不将某个第三方包自动称为官方扩展。安装依实际授权与宿主规则执行，不暗中改变供应商、登录或计费配置。
3. 启用或安装后，重新发现工具，用无外部副作用的小任务核实独立执行、结果返回和停止方式；仅有扩展文件不算能力就绪。
4. 官方未提供可用途径、安装受阻或验证失败时，报告具体阻塞并保留交接，不宣称所有 Agent 都存在官方扩展，也不默认改装第三方替代品。

能力就绪前只准备协调文档、派工单和阻塞记录，不进入实现或验证编排；不能让主协调者兼任实现与独立验收、伪造多个角色的意见或标记已通过完整团队验证。Bot 体系未明确选择本技能时，直接沿用其原生流程，不走此安装分支。

## 创建与隔离

- 当前主 Agent 始终承担 coordinator。按职责启动子 Agent，标题使用“角色＋卡号”，别名来自可选配置。
- 需要严格独立审查时，给审查者任务卡、待审版本、适用规则和原始证据，不提供预期结论或指示其必须通过。使用宿主支持的最少上下文继承模式，例如 `fork_turns=none`；只有实际可用时才写该参数。
- 其他岗位也优先传明确任务和文件路径；需要完整历史时再使用宿主支持的继承方式。目标项目已有 `roleNotes` 时，派工提示必须带上该岗位的备注，不能只口头记住。
- 不自行指定模型覆盖或升级成本；继承宿主默认，除非用户或适用规则明确要求某个可用配置。角色名不绑定模型。
- 并发上限取用户限制、宿主可用容量和当前任务需要的最小值，给主协调者保留槽位。槽位不足就串行，不嵌套创建一层协调者绕过限制。
- 子 Agent 不继续派工；如确需拆分，向主协调者提出。防止子树无界增长或同一卡出现多个实现者。
- 同一卡的代码由唯一实现者拥有。不同卡优先使用隔离 checkout/worktree；对共享文件和接口的依赖先确定顺序。评审在固定提交读取，避免主工作树分支切换造成串版。
- 写权限由派工边界和实际工具控制共同约束；角色名、提示词、独立会话都不等同 OS 沙箱。共享桌面/浏览器、端口、数据库和远端服务要实际核对冲突。

## 推进与结束

派工后利用结果通知或宿主等待工具，期间推进无依赖工作；不要用秒级轮询制造空转。阶段就绪时及时读取交还、核实证据、写回检查点，再启动下一阶段。

返工可以续派原实现者，独立验收仍由不同执行者负责；需全新视角时创建新审查实例并传当前证据。失联后重建实例先核对副作用，不能直接重跑发布、迁移或其他不明写入。

结束时收回任务、归档交还并释放协调资源占用。有结束/释放工具则依说明使用；只有中断工具时，停止执行并标记 retired，不声称已永久删除会话或平台日志。不要为了“销毁”去删除外部文档、工作树或其他项目资源。

用户暂停时阻止后续派工，通知或中断活动子任务，核实外部 CLI/命令是否仍在运行；中断一个模型回合不保证已经停止它启动的所有系统进程。记录剩余运行项和恢复点。

## 独立行为验收建议

对复杂新版本，在隔离临时目录用真实子 Agent 验证决策行为：提供一张样例卡、不同版本证据、实际工具约束和用户授权，让它按技能组织下一步。检查是否真实识别版本错配、拒绝越职写回、尊重暂停与数据边界，而非仅检查文件里是否出现某句话。

测试只操作临时工件，不向真实 Bot 发消息、不运行生产部署、不触发发布或接管用户项目。把结果写入技能项目的外部验收记录，按发现修订；模拟结果不冒充真实产品交付闭环已跑通。
