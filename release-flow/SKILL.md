# release-flow

## 目标

把项目发布流程统一成一条可重复执行的流水线：

1. 识别版本
2. 构建产物
3. 校验产物
4. 提交代码
5. 打 Tag
6. 创建或更新 Release
7. 上传资产

## 执行原则

- 默认零配置，优先自动识别项目类型。
- 遇到不确定的地方，再向用户确认。
- 每一步都要能恢复，不要把状态写丢。
- 产物命名要带版本号，避免无版本文件名。

## 识别顺序

优先按仓库结构识别项目类型：

1. `tauri`
2. `node/web`
3. `python`
4. `go`
5. `rust`

如果同时命中多个类型，就结合用户目标和仓库上下文决定。

## 通用步骤

1. 读取当前版本。
2. 更新版本文件。
3. 执行构建。
4. 收集产物。
5. 校验产物存在且命名正确。
6. 提交并打 Tag。
7. 创建或更新 Release。
8. 上传资产。
9. 输出发布结果。

## 预检要求

- 先看当前分支模型，不要强行要求某个固定分支。
- 检查命令兼容性，避免在不同平台上出错。
- 如果本机无法生成某类资产，要提前说明。

## 输出要求

- 版本号
- commit id
- tag
- Release 链接
- 资产列表
- 缺失资产和原因（如有）
